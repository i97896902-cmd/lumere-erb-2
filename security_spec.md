# Security Specification: Luméré Group Multi-Company ERP

## 1. Core Multi-Tenant & RBAC Invariants
1. **Default Deny**: Every Firestore collection and Firebase Storage bucket path denies unauthenticated and unauthorized reads/writes by default (`match /{document=**} { allow read, write: if false; }`).
2. **Verified-Identity Write Enforcement**: Every Firestore write (`create`, `update`, `delete`) enforces `request.auth != null && request.auth.token.email_verified == true` (`isVerifiedUser()`), preventing unverified or spoofed email tokens from mutating data.
3. **Strict Company Isolation**: Every company-owned document (`users`, `departments`, `clients`, `projects`, `tasks`, `tasks/{taskId}/comments`, `notifications`, `activity_logs`, `equipment`, `equipmentHistory`, `reports`) must carry a valid `companyId`. Non-`SUPER_ADMIN` users may only read or query documents where `companyId == currentUserCompanyId()`.
4. **4-Tier Role Hierarchy**:
   - `SUPER_ADMIN`: Full access across `LUMERE GROUP` and all subsidiaries. Verified via Firebase Auth Custom Claims (`request.auth.token.role == 'SUPER_ADMIN'`), `/admins/{uid}`, or verified bootstrap email `lumerecompany@gmail.com` (`email_verified == true`).
   - `COMPANY_ADMIN`: Administrative control strictly limited to their own `companyId`; can assign `MANAGER` or `EMPLOYEE` roles only; cannot modify themselves, `SUPER_ADMIN`, or peer `COMPANY_ADMIN` accounts; cannot spoof `approvedBy`; cannot create companies or cross company boundaries.
   - `MANAGER`: Operational management (`clients`, `projects`, `tasks`, `equipment`, `reports`) strictly within their own `companyId`.
   - `EMPLOYEE`: Read-only access to their own company workspace; can only progress non-terminal assigned tasks (`In Progress` -> `Review`), upload bounded attachments, and post comments on tasks inside their own company.
5. **Standalone Validation Blueprints (Anti-Update-Gap & Anti-Shadow-Field)**: Every collection enforces a dedicated `isValid[Entity](incoming())` helper on BOTH `create` and `update`, guaranteeing `hasAll` required fields, `hasOnly` allowed keys (blocking shadow fields), `.size()` bounds on every string, bounded ranges on numbers, and `.size() <= MAX` + element-type checks on every array.
6. **Path ID Hardening & Split `get`/`list`**: Every single-document operation (`get`, `create`, `update`, `delete`) validates document IDs via `isValidId()` (`^[a-zA-Z0-9_\-]+$`, `<= 128` chars), while `allow list` rules evaluate `resource.data` directly without delegating filtering to the client.
7. **No Cross-Company Assignment or References**: Creating and updating tasks and equipment requires `assignee.companyId == doc.companyId`, `project.companyId == doc.companyId`, and `client.companyId == doc.companyId`. Creating notifications verifies the recipient belongs to the target company or is a `SUPER_ADMIN`. Creating `equipmentHistory` verifies parent equipment exists in the same company.
8. **Immutable Audit Trails & Fields**: `activity_logs` and `equipmentHistory` forbid `update` and `delete` for all roles, including `SUPER_ADMIN`, and require `actorId == request.auth.uid` on create. `createdAt`, `createdBy`, and `generatedBy` are immutable on updates.
9. **Non-Destructive Company Lifecycle**: `companies` documents forbid client deletion (`allow delete: if false;`), require `slug == companyId` on create, forbid deactivating or changing `type` on `lumere-group`, and archive subsidiaries via `status: 'inactive'`.
10. **Storage Path Isolation**: Uploads are scoped under `/companies/{companyId}/...` with ID format validation, MIME type allow-lists, size ceilings (5MB images, 15MB attachments), and explicit `delete` authorization separate from `create, update`.

## 2. Multi-Tenant "Dirty Dozen" Attack Scenarios
1. **Cross-Company Read Attack**: A `COMPANY_ADMIN` or `EMPLOYEE` from `ordark` attempts to `get` or `list` tasks, clients, or users belonging to `nex-aura`. -> **DENIED**.
2. **CompanyId Tampering Attack**: An active `EMPLOYEE` or `COMPANY_ADMIN` attempts to change their own `companyId` from `ordark` to `lumere` or `lumere-group`. -> **DENIED**.
3. **Role Escalation & Unverified Admin Spoofing**: A `COMPANY_ADMIN` attempts to promote themselves or another user to `SUPER_ADMIN`, modify a peer `COMPANY_ADMIN`/`SUPER_ADMIN`, or an unverified `lumerecompany@gmail.com` token (`email_verified: false`) attempts bootstrap elevation. -> **DENIED**.
4. **Cross-Company Task / Equipment Assignment (Create & Update)**: A `MANAGER` in `lumere` attempts to create or reassign a task or equipment item to an employee whose `companyId` is `nex-aura`. -> **DENIED**.
5. **Cross-Company Project/Client/History Link**: A task references a `projectId`/`clientId` owned by another company, or an `equipmentHistory` record references equipment from another company. -> **DENIED**.
6. **Skip-Review Task Completion, Self-Approval & Terminal State Tampering**: An `EMPLOYEE` attempts to set their task to `Completed`, set `reviewStatus: 'approved'`, or reopen an already `Completed`/`Cancelled` task. -> **DENIED**.
7. **Parent Company Deletion/Deactivation/Type Mutation**: Attempting to delete `/companies/lumere-group`, set `status: 'inactive'`, change its `type` away from `'parent'`, or create a company with mismatched `slug != companyId`. -> **DENIED**.
8. **Activity Log Tampering / Spoofing**: Attempting to modify/delete an `activity_logs` entry or create a log with another user's `actorId`. -> **DENIED**.
9. **Cross-Company Notification Spam & Pre-Read Forgery**: A user from `ordark` attempts to write a notification targeting a `nex-aura` employee, create a notification with `read: true`, or write a non-boolean value into `read`. -> **DENIED**.
10. **Shadow Field Injection & Value Poisoning**: Injecting undeclared keys (e.g., `isAdmin: true`) or oversized >5KB strings / unbounded arrays (`attachments`, `teamMemberIds`, `adminIds`) on create or update. -> **DENIED**.
11. **Storage Cross-Company Access & Oversized/Executable Uploads**: Reading, uploading, or deleting files under another company's storage prefix, or uploading `.exe` or >15MB files. -> **DENIED**.
12. **Out-of-Range Progress, Immutable Timestamp Tampering & Path ID Poisoning**: Writing `completionPercentage: 250`, altering `createdAt`/`createdBy`, or passing 1KB junk document IDs. -> **DENIED**.

## 3. Phase 3 Red Team Audit & Hardening Delta
1. **`firestore.rules` — Task Update Assignee Loophole**: Added `assigneeMatchesCompany` on `tasks/{taskId}` update. **Patched.**
2. **`firestore.rules` — `COMPANY_ADMIN` Peer/Super-Admin Tampering**: Restricted `COMPANY_ADMIN` updates to `MANAGER`/`EMPLOYEE` targets, non-self, and immutable `uid`/`email`/`companyId`. **Patched.**
3. **`firestore.rules` — Company Enumeration & Parent Deactivation**: Restricted `companies` listing to `SUPER_ADMIN` and pending onboarding users; blocked deactivating `lumere-group`. **Patched.**
4. **`firestore.rules` — Document ID Validation & String Bounds**: Added `isValidId(id)` and string size caps. **Patched.**
5. **`storage.rules` — Logo Enumeration & Delete Null-Resource Bug**: Scoped logo reads per company and split `create, update` vs `delete`. **Patched.**
6. **`functions/src/index.ts` — Unverified Email Bootstrap & `COMPANY_ADMIN` Peer Guard**: Enforced `email_verified === true` and peer-admin guards. **Patched.**
7. **Production Auth Guard**: Enabled strict Google Sign-In in `AuthContext.tsx`. **Patched.**

## 4. Phase 4 Production Pre-Launch Rules Audit & Hardening Delta
Comprehensive Eight-Pillar & ESLint (`@firebase/eslint-plugin-security-rules`) audit prior to production rollout identified and closed 11 additional gaps:
1. **Verified-Email Write Mandate (`isVerifiedUser()`)**: Enforced `request.auth.token.email_verified == true` on EVERY `create`, `update`, and `delete` rule across all 13 collections.
2. **Employee Task `reviewStatus` Self-Approval & Terminal State Lock**: Blocked `EMPLOYEE` from setting `reviewStatus` to `'approved'`/`'rejected'`, blocked mutating `Completed`/`Cancelled` tasks, and fixed a compatibility bug where updating `completionPercentage` or `attachments` on a `Pending`/`Rejected` task previously required `status in ['In Progress', 'Review']`.
3. **Standalone `isValid[Entity]` Blueprints & Strict Key Allowlists (`hasOnly`)**: Added 11 dedicated validation functions (`isValidCompany`, `isValidUser`, `isValidDepartment`, `isValidClient`, `isValidProject`, `isValidTask`, `isValidComment`, `isValidNotification`, `isValidActivityLog`, `isValidEquipment`, `isValidEquipmentHistory`, `isValidReport`) enforced on BOTH `create` and `update`, eliminating shadow-field injection and value-poisoning across all updates.
4. **Total Array Guarding**: Added `.size() <= MAX` + element-type validation on `adminIds` (50), `assignedEmployeeIds` (50), `teamMemberIds` (100), `files` (50), `coAssignees` (20), and `attachments` (20).
5. **Split `allow get` vs `allow list` + `isValidId` Path Hardening**: Split every `allow read` into explicit `allow get` (guarded with `isValidId`) and `allow list` (evaluating `resource.data` without path-ID checks).
6. **Self-Update Action Allowlist on `users/{userId}`**: Replaced denylist `!affectedKeys().hasAny(...)` with strict `affectedKeys().hasOnly(['displayName', 'fullName', 'phone', 'department', 'position', 'jobTitle', 'photoURL', 'companyId', 'companyName', 'updatedAt'])` and verified `approvedBy == request.auth.uid` on `COMPANY_ADMIN` approvals.
7. **Notifications Anti-Spam & Type Integrity**: Enforced `read == false` on create, `recipientMatchesCompanyOrSuperAdmin(userId, companyId)` to block cross-company notification spam while allowing subsidiary-to-`SUPER_ADMIN` review alerts, and strict `affectedKeys().hasOnly(['read'])` + `read is bool` on update.
8. **Immutable Field Guards**: Enforced `isImmutableField('createdAt')` across all mutable collections, `isImmutableField('createdBy')` on `tasks`, `isImmutableField('generatedBy')` on `reports`, `slug == companyId` on `companies` create, and `type == 'parent'` protection on `lumere-group`.
9. **Master Gate & Relational Integrity Hardening**: Verified parent task `exists(...)` on all `/tasks/{taskId}/comments/{commentId}` operations, verified parent equipment `exists(...)` + company match on `equipmentHistory` create, and added `assigneeMatchesCompanyIfPresent` / `projectMatchesCompanyIfPresent` on `equipment` create & update.
10. **Pending Onboarding Department Scope Alignment**: Restricted pending users from reading parent holding (`lumere-group`) departments in `firestore.rules` and aligned `DataService.subscribeDepartments` / `App.tsx` with `where('companyId', '!=', 'lumere-group')`.
11. **Blueprint Synchronicity**: Added `Report` / `/reports/{reportId}` to `firebase-blueprint.json` and synchronized all `maxLength` and `enum` bounds verbatim with `firestore.rules`.
